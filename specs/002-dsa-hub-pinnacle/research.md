# Phase 0 Research: DSA Hub — Pinnacle Cross-Source

**Date**: 2026-04-26
**Spec**: [spec.md](./spec.md) (post-clarify; 5 Q&As recorded)
**Plan**: [plan.md](./plan.md)

This document records the design decisions made before Phase 1 (data-model + contracts). Each entry follows the **Decision / Rationale / Alternatives considered** format. Every entry corresponds to either an in-flight ADR (016–021 placeholders) or a non-ADR-worthy implementation choice that still benefits from being recorded.

---

## R1 — Workspace identity and lifecycle

**Decision**: A **Workspace** is identified by the existing per-tab `sessionStorage` UUID (already produced by `frontend/src/lib/session.ts`). Backend keys all workspace-scoped state by this UUID via the existing `X-DSA-Session-ID` header, with a new `X-DSA-Workspace-ID` accepted as a synonym for one minor version (FR-006). Workspace state lives only in the browser session + a backend in-memory `WorkspaceRegistry`; nothing persists server-side beyond ephemeral cache.

**Rationale**: Q1 chose per-tab/session scoping. The existing per-tab UUID model already has invariants (one UUID per tab, lost on close) that match the desired behavior exactly. Reusing it avoids a parallel identity scheme.

**Alternatives considered**:
- *Cognito user → workspace*: rejected per Q1 (deferred to v2+).
- *Project/firm slug*: rejected per Q1 + Q2 (would put long-lived state under workspace identity, but Q2 chose per-connection).
- *New random UUID*: rejected — duplicates the existing `sessionId`.

**ADR**: `docs/adr/016-multi-connection-workspace.md` (in-flight).

## R2 — Per-connection durable storage layout

**Decision**: Each connection's durable state (semantic graph, discovery cache snapshot, registered-products index, activity-log entries scoped to that connection) lives in a per-connection store keyed by a stable `connection_id`.

- **`connection_id`** = SHA-256 of `(driver_type, normalized_endpoint, scope)`, e.g., `sha256("snowflake|lga76011.snowflakecomputing.com|PINNACLE_FINANCIAL_DEMO_ASINGH.ANALYTICS")`. Stable across tabs/sessions so reopening produces the same id.
- **Local mode** (`STORAGE_BACKEND=local` or unset): SQLite file per connection at `~/.dsa-hub/connections/<connection_id>/store.db`. Schema: `entities`, `attributes`, `metrics`, `joins`, `physical_bindings`, `products`, `activity_log`. Migrations via `alembic` in `src/platform_agent/semantic/migrations/`.
- **Deployed mode** (`STORAGE_BACKEND=dynamodb`): single-table `DSAHubConnectionStore` with PK `connection_id` and SK `entity_kind#entity_id` (matches existing AgentCore Memory pattern). Sparse GSI on `(connection_id, kind)` for kind-scoped queries.

**Rationale**: Q2 chose per-connection scoping. SQLite is the simplest local store with first-class Python support, matches the spirit of "no server-side state in local mode," and survives tab close because the file lives outside the browser. DynamoDB single-table is the established repo pattern for deployed mode.

**Alternatives considered**:
- *One file per kind* (entities.json, metrics.json, …): rejected — joins/queries become awkward, no transactional consistency.
- *Single global SQLite for all connections*: rejected — couples connections together, complicates the Q2 contract that each connection's graph is independent.
- *Postgres metadata DB*: rejected — adds a service to local-mode runtime and contradicts "no server-side persistence" intent.

**ADR**: `docs/adr/017-per-connection-semantic-graph.md` (in-flight).

## R3 — Iceberg/Glue connection as a first-class driver

**Decision**: Add `IcebergDriver` implementing the existing `DatabaseDriver` protocol (`src/platform_agent/drivers/base.py`), backed by **pyiceberg** + boto3 Glue client. The driver is symmetric — it both scans/queries existing Iceberg tables (so TTYD can read from registered products) AND writes new tables (so the mapping-agent can register provisioned products there).

- **Connection scope**: `(glue_database, s3_warehouse_uri, region)`.
- **`scan_metadata`** uses Glue `GetTables` + Iceberg `Catalog.load_table()` to list schema.
- **`run_query`** uses pyiceberg's `Table.scan()` with column pushdown + a 250-row limit applied at the scan layer (not just post-fetch) for the FR-018 cap.
- **Write path** (mapping-agent only) uses `Table.append()` for the materialized join result; DDL goes through `Catalog.create_table()`.
- **dbt config**: `dbt-glue` adapter, profile generated by `generate_dbt_project` for the Iceberg target.

**Rationale**: Per Q3 the user explicitly adds the Iceberg connection. Treating it as a peer driver under the existing protocol means tools, UI cards, and TTYD work without special-casing. pyiceberg is the actively-maintained Python-native Iceberg client and avoids a JVM dependency.

**Alternatives considered**:
- *Athena over Iceberg*: rejected — adds an Athena query path and AWS coupling for read; pyiceberg reads directly from S3 metadata.
- *Glue interactive sessions / Spark*: rejected — heavyweight; killed local-mode parity.
- *Treat Iceberg only as a write target, not a connection*: rejected by Q3 — the user explicitly wants Iceberg as a first-class connection, and the auto-validation flow needs to query it via TTYD post-provisioning (FR-031).

**ADR**: `docs/adr/020-provisioning-orchestration-iceberg.md` (in-flight; covers both the orchestration and the driver since they were decided together).

## R4 — Cross-source query execution: in-process DuckDB scratchpad

**Decision**: When the active lens is "all sources" and a question requires combining ≥2 connections, the planner pulls bounded subsets from each source via that source's existing `run_query`, registers them as DuckDB views, and runs the join in an in-process DuckDB session. Caps: 250 rows per source pull, 5,000 rows for the joined result. Truncations are surfaced explicitly in the response.

- **Tool**: `src/platform_agent/tools/duckdb_scratchpad.py` exposes `cross_source_query(per_source_pulls: list[SourcePull], join_sql: str) -> Result` where each `SourcePull` is `(connection_id, sql, max_rows=250)`.
- **Read-only enforcement**: the join SQL passes through the same SELECT/WITH-only regex used for source queries; DuckDB session is created with `read_only=False` (DuckDB requires writability to register views) but only DDL for views and SELECTs against them are permitted by the wrapper.
- **Lifetime**: one DuckDB session per cross-source TTYD turn; disposed at the end. No data persisted.

**Rationale**: DuckDB is the established choice for in-process analytical joins in Python: zero deploy footprint, columnar engine, supports SQL parity that the LLM planner already speaks. Caps protect demo from runaway joins. Per-turn lifetime means no stale state.

**Alternatives considered**:
- *Federated query in Snowflake (external tables over Postgres)*: rejected — requires Snowflake-side configuration the customer demo doesn't control, and creates a Snowflake bias.
- *Materialize joins to Iceberg then query*: rejected — turns every TTYD question into a provisioning run; latency unacceptable (SC-005 ≤5s).
- *Pull both into pandas + merge*: rejected — pandas merges are imperative and don't take SQL from the LLM directly; adds a translation layer.
- *Trino/Presto*: rejected — heavyweight infrastructure for a per-tab demo.

**ADR**: `docs/adr/018-cross-source-query-via-duckdb.md` (in-flight).

## R5 — Pill generation: schema-driven, not hardcoded

**Decision**: A `pill-agent` (Strands, **Opus 4.7**) runs once per workspace after both source connections are live. Inputs: per-connection discovery summaries (entities, attributes, sample values) + the workspace cross-source coverage map (which entities have shared business keys across connections). Output: a list of `PillSuggestion` records (≥6) each with title, source backings, declared Iceberg target name, estimated build time, and a seed PRD body. The Pinnacle pills (Client 360, Revenue Waterfall, Advisor Productivity, Client Profitability, Trade Cost Attribution, Budget vs. AUM Reality) are provided to the agent **as in-context examples** (few-shot), not as hardcoded outputs.

**Rationale**: FR-011 + FR-012 + SC-010 require pills to be schema-driven so non-Pinnacle datasets produce different pills. Few-shot prompting with the six Pinnacle examples gives the model a quality bar without baking the answers in.

**Alternatives considered**:
- *Hardcoded pill catalog with template substitution*: rejected — violates SC-010; one demo dataset's pills wouldn't generalize.
- *Sonnet 4*: rejected — pill generation is the cross-source reasoning task most likely to need Opus 4.7's multi-table judgment, per the input brief's "escalate to Opus 4.7 for redundancy reasoning, cross-source query planning, and pill generation."
- *Pure rules engine* (no LLM): rejected — cannot produce business-meaningful pill titles.

**ADR**: `docs/adr/021-pill-generation.md` (in-flight).

## R6 — Provisioning orchestrator: 7-agent DAG with SSE event stream v2

**Decision**: A `ProvisioningOrchestrator` runs the 7-agent DAG in dependency order with the following edges:

```
schema → pipeline → model → quality → mapping ─┬─→ semantic ─→ delivery
                                               └─→ (mapping is the Iceberg/catalog write; semantic + delivery
                                                   read the registered table back)
```

- **Per-agent retry** (FR-029): on failure, only the failed agent and its downstream dependents re-run; completed upstream artifacts are reused (cached per `run_id`).
- **Event stream**: `GET /workflow/provision/{run_id}/events` is SSE with **schema v2** (extends existing v1 event model). New event kinds: `agent.started`, `agent.progress`, `agent.completed`, `agent.failed`, `kpi.tick`, `artifact.produced`, `validation.started`, `validation.result`, `run.completed`, `run.needs_replan`. Each event carries `run_id`, `agent_id`, `seq`, `ts`. Heartbeat every 10s reuses existing `SSEEmitter` passive heartbeat.
- **State persistence**: orchestrator state (per-run agent statuses, artifacts produced, KPI series) lives in-memory keyed by `run_id`; tab close ends the SSE stream but the state survives in backend memory for the run's natural lifetime. Per-connection durable assets (semantic graph entries, registered products, activity-log entries) are written through the per-connection store as the run progresses, so the durable record survives even if the SSE consumer disconnects.

**Rationale**: 7-agent dependency order taken directly from the spec input. Per-agent retry implements FR-029 surgically. SSE schema v2 is additive over v1, preserving the existing parser path; new event kinds are version-gated by a `v: 2` field on the wire.

**Alternatives considered**:
- *Step Functions for orchestration*: deferred to deployed-mode — Step Functions adds AWS coupling for local-mode and is harder to test from pytest. The existing `patterns/migration-agent` Step Functions plan remains the deployed-mode option, but for v1 in-product flow we run the DAG in-process (Python `asyncio`).
- *Single monolithic agent*: rejected — kills the DAG visualization (Story 3) which is the headline UX for provisioning.
- *Polling-based progress*: rejected — SSE is already the established pattern in the repo and provides 1s update latency (US-3 acceptance #2).

**ADR**: `docs/adr/020-provisioning-orchestration-iceberg.md` (in-flight; same ADR as R3 since they're co-decided).

## R7 — Redundancy gate against the target connection's graph

**Decision**: A `redundancy-agent` (Strands, **Opus 4.7**) runs between PRD draft and acceptance. Inputs: the drafted PRD's declared entities, metrics, and target Iceberg connection. Reads via `semantic_graph_read` tool against the target connection's graph (per Q2, NOT against source-connection graphs). Output: a `RedundancyReport` with state ∈ {`net_new`, `partial_overlap`, `duplicate`} plus per-overlap details and reuse-or-override choices.

- Block flow only on `duplicate` until the user records an override rationale.
- Diff format: side-by-side proposed vs. existing entity/metric, with overlap percentage.

**Rationale**: Per FR-026 + Q2, the target connection (typically the user-added Iceberg/Glue connection) holds the durable record of previously-shipped products; it's the right place to check for redundancy. Source-connection graphs hold raw schema entities (clients, accounts) that always overlap with anything that selects from those sources — checking against them would surface false positives.

**Alternatives considered**:
- *Check against all connections' graphs in the workspace*: rejected per Q2 — would reintroduce cross-connection reconciliation logic.
- *Check against a global registry*: rejected per Q2 — there is no global registry in v1.
- *Sonnet 4 for redundancy*: rejected per input brief — escalation to Opus 4.7 explicit.

**ADR**: `docs/adr/019-redundancy-gate.md` (in-flight).

## R8 — Validation threshold gate and product registration states

**Decision**: Provisioning's `delivery-agent` runs auto-validation by sending each PRD business question through the existing TTYD path (with the "all sources" lens, post-registration). Each result is judged by an LLM-as-judge (`Opus 4.7`) against expected ranges captured in the PRD. The pass rate is computed as `passed / total`.

- **Threshold** = 80% by default (matches SC-004), configurable via env (`DSA_HUB_VALIDATION_THRESHOLD`).
- **≥ threshold** → product state `final`; mapping-agent has already registered it, delivery-agent flips a `tttd_exposed = True` flag in the per-connection product registry; TTYD `cross_source_query` includes it in its source list.
- **< threshold** → product state `provisional`; the table is registered in Glue and visible on the Semantic page, but `ttyd_exposed = False`; the run emits `run.needs_replan`. A "Re-run from failed step" affordance re-executes only the validation step (and, optionally, the upstream agent that produced the schema gap, e.g., model-agent for a missing column).
- **Rerun success** that lifts pass rate ≥ threshold flips `ttyd_exposed = True` atomically.

**Rationale**: Q5 chose threshold-gate behavior with default 80% (SC-004). LLM-as-judge for validation matches the existing AgentCore evaluator pattern (Article IV). The provisional state is a soft fence — the artifact exists but isn't yet "delivered" — preserving Article VIII's "no silent failure" while not destroying provisioning work.

**Alternatives considered**:
- *Roll back the Iceberg registration on partial fail*: rejected per Q5 (option A explicitly not chosen).
- *Auto-rerun without user input*: rejected — silently spending a build cycle without user awareness violates Article VIII (loading/error states must be visible).
- *Hardcode 80%*: rejected — config-driven for future flexibility, but defaults to the spec'd line.

**ADR**: extension of `docs/adr/020-provisioning-orchestration-iceberg.md` (in-flight).

## R9 — Demo-mode multi-source scenario

**Decision**: Extend the existing `frontend/src/hooks/useAgent.demo.ts` pre-scripted engine with a Pinnacle multi-source scenario. Demo mode fakes:
- Two source connections (Postgres + Snowflake) reaching `live` state with seeded KPI counts.
- A pre-staged Iceberg/Glue connection (already-attached at workspace bootstrap).
- 8 business-process cards with the named volumes from FR-042.
- 6 pre-canned pills (Pinnacle-specific) — flagged with `demo: true` so the schema-driven pill agent isn't invoked.
- A Client 360 PRD click → redundancy gate → 7-agent DAG with scripted timing → registered Iceberg table → green Validation Card → TTYD answer with source chips.

**Rationale**: FR-041 mandates demo-mode parity for the multi-source narrative. Reusing the existing demo engine avoids a parallel mocking system. Scripted timing keeps the showcase deterministic.

**Alternatives considered**:
- *Run real agents against fixture data*: rejected — too slow, network-dependent.
- *MSW (Mock Service Worker)*: rejected — heavier than the existing demo engine and not needed for an offline demo.

**ADR**: not ADR-worthy on its own; mentioned in `docs/adr/016-multi-connection-workspace.md`.

## R10 — Color palette extension for status semantics

**Decision**: Keep phData palette (Navy / Blue / Teal / Orange) for all chrome, surfaces, typography, and primary chart colors. Add **two semantic-only roles**:
- `--status-success: #16A34A` (a darker, brand-compatible green)
- `--status-error: #DC2626` (a darker, brand-compatible red)

Status colors are used **only** for: agent DAG node states (active = phData Teal pulse, complete = success-green, failed = status-error), Validation Card ✓/✗, and connection card pulse dots. All ambient UI continues to use phData strict.

**Rationale**: Article V demands phData strictness, but Story 3 + Story 6 require unambiguous binary status semantics. Adding two semantic-only roles (not five accent colors as in the original brief) is the minimum deviation. The chosen green/red are darker than the brief's pastels and harmonize better with Navy.

**Alternatives considered**:
- *Use the brief's full accent palette* (`#00d4a0`, `#fbbf24`, `#4f8fff`, `#a855f7`, `#f472b6`): rejected — five off-brand colors is a Article V violation without justification; only success/error are load-bearing.
- *Use icons + greyscale only* (no status color): rejected — color-blind-unsafe for binary status; "green check / red x" is the universal idiom.
- *Use phData Orange for "failed"*: rejected — Orange is an accent color, not a danger signal; conflates with active states.

**Documented in**: Complexity Tracking row 1 of plan.md, plus `docs/adr/020-provisioning-orchestration-iceberg.md`.

## R11 — Bootstrap script: Pinnacle Postgres seed (replace Northwinds)

**Decision**: `scripts/bootstrap.sh` replaces the Northwinds seed with a Pinnacle Financial seed (`scripts/seed_pinnacle.sql`) targeting the same `platform-agent-northwinds` RDS instance (renaming optional, deferred to Terraform module update). Tables and row volumes per FR-042:

- AP: `vendors`, `purchase_orders`, `invoices` (336), `payments` (308), `expense_lines` (336), `gl_accounts` (16), `cost_centers` (8).
- Billing: `clients` (30), `fee_schedules`, `fee_invoices` (1,680), `billing_cycles` (1,680 closed + 70 open), `fee_adjustments` (80).
- CRM: `meetings` (335: 175 quarterly + 160 strategy), `opportunities` (90: 31 won + 30 open + 29 lost), `advisor_clients` (effective-dated), `engagement_metrics` (720).
- Portfolio Mgmt: `accounts` (70), `trades` (420), `rebalancing_events` (280), `holdings` (2,100), `strategies` (12).
- Performance: `aum_snapshots_daily` (6,300), `benchmark_returns` (630).
- FP&A: `budget_lines` (18,432), `forecasts` (Q1+Q2 = 600M+), `forecast_actuals` (~305M avg).
- GL: `journal_entries` (69), `journal_lines` (138), `fiscal_periods` (24).
- HR: `employees` (15), `departments` (4), `cost_allocations` (17).

A separate `scripts/seed_pinnacle_snowflake.sql` (run against the demo Snowflake account) preserves the existing analytical mirror tables (`DIM_CLIENT`, `FCT_AUM_HISTORY`, `FCT_PERFORMANCE_ATTRIBUTION`, etc.) with shared business keys (`client_id`, `account_id`, `strategy_id`).

**Rationale**: FR-042 explicit. Reusing the existing RDS instance avoids new Terraform churn for v1; the schema swap is data-only.

**Alternatives considered**:
- *Stand up a second RDS instance*: rejected for v1 — unnecessary cost; bootstrap idempotency suffices.
- *Synthetic data generation in Python*: rejected — SQL seed is faster, deterministic, and easier to inspect.

**Documented in**: not ADR-worthy; covered in quickstart.md and the bootstrap script itself.
